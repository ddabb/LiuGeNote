# 上架截图返工实录：尺寸缩放、覆盖事故与安全替换

首批三端截图交付后被打回一处：平板图是模拟器原生的 2400×1600，而上架文档写的是 1920×1280。返工远比"缩放一下"曲折——包括一次把五张原片全部清零的覆盖事故，和一个"今日已答"锁死答题页的重截难题。

## 返工起因：原生分辨率不等于上架规格

平板首批截图按模拟器原生 2400×1600 交付，与上架文档标注的 1920×1280 规格不符，需要返工。市场上架要求写的是"最低尺寸 1920×1280、宽高比 3:2"，2400×1600 严格说也满足比例与下限，但交付规格应与文档逐字对齐——审核、比对、归档都以文档为准，"差不多"就是返工的种子。

处理方式定为：原生捕获保持像素精确（坐标导航、布局校验都基于原生分辨率），交付前统一等比缩放到 1920×1280。2400×1600 缩到 1920×1280 恰好是 0.8 的等比缩放，3:2 比例无损。

## 事故：一次"参数无效"毁掉五张原图

缩放脚本第一次跑就出了事故：五张原片全部变成 0 字节。事故链有两环：

1. PowerShell 里调 System.Drawing 的三参重载 Bitmap.Save(path, codec, encoderParams) 抛出 ArgumentException"参数无效"——EncoderParameters 在 PowerShell 互操作层出了名地不稳定，是 GDI+ 的经典坑；
2. 更致命的是流程：脚本"先 Save 覆盖式输出，再 Move-Item 归位"，Save 抛异常后没有中止，Move-Item 照常执行，把残留的空文件盖到了原图上。

五张精心摆好状态的截图——继续阅读卡、66% 阅读进度、答对的每日一题——瞬间归零。教训只有一句：绝不在未校验前覆盖不可再生的源文件。

## 安全流程：先出独立文件，校验后再替换

重建后的流程把缩放输出与原图彻底分开：缩放结果先写独立文件，校验通过后才允许替换。

1. 缩放输出写到独立的目标文件（原名加尺寸后缀），原图始终不动；
2. 校验三项：文件大小大于 0、像素尺寸恰为 1920×1280、JPEG 质量档位符合预期；
3. 全部通过后才执行替换归位。

任何一步失败，原图都完好无损，重跑即可。缩放实现也从 System.Drawing 换成了 WPF（PresentationCore 加 WindowsBase）：TransformedBitmap 配 0.8 的 ScaleTransform，再用 JpegBitmapEncoder 以 92 的质量档编码——纯托管 API，没有 GDI+ 互操作的坑。该质量档下五张图 133~221KB，远低于 5MB 上限，UI 截图目测无损失。

## 重截技巧：每日一题已答状态的处理

重截每日一题时当日题已答过，答题页只会显示完成态。模拟器上想让"今天"重新变成"没答过"，常规手段全部碰壁：

- 改系统时间：busybox date -s 的时间戳格式能被解析，但报 "Operation not permitted"——shell 是 uid 2000 的普通身份，设备上没有 su；
- 改时区：param set persist.global.timezone 直接 errNum 1001 权限拒绝。

最终用临时构建绕过：把 QuizManager 的 isDailyDone 临时改为恒返回 false，打包安装后重答、截取判分态，截完立即还原代码、重建、装回干净版本。副作用可控——多答一题只让累计答对数加一，界面上不可见。相比改系统时间，这条路不污染设备状态，还顺带验证了打卡状态确实由 preferences 的 dailyDoneDate 键驱动。

## 结果与教训

返工后的十五张截图全部对齐规格：手机 1080×1920、平板 1920×1280、2in1 1920×1080。三条沉淀：

1. 交付规格以文档为准逐字对齐，原生分辨率只是生产素材；
2. 覆盖类操作永远"先写副本、校验、再替换"；GDI+ 的 EncoderParameters 在 PowerShell 里不可信，图像编码优先走 WPF 托管管线；
3. 状态锁定的页面要重截，优先做临时构建绕过，不要跟系统时间较劲——模拟器的 shell 权限根本不允许。

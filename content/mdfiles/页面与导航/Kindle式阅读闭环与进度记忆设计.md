# Kindle 式阅读闭环：进度记忆、会话统计与读后引导

列表、详情、搜索都有了之后回头看：文章读一半退出，再进来从零开始；读完一篇就"断了"，没有下一步。这轮迭代补的就是这一环——从"能看"到"接着读"。

## 一、进度模型：只进不退

每篇文章一个整型键 `p_<slug>`（0-100），存本地 preferences。写入规则只有一条：**新值低于旧值时忽略**。

```typescript
static setProgress(slug: string, pct: number): void {
  const v: number = Math.round(Math.min(100, Math.max(0, pct)));
  const cur: number = ReadingTracker.getProgress(slug);
  if (v < cur && cur < 100) {
    return; // 向上翻回不丢最深阅读位置
  }
  ReadingTracker.put(ReadingTracker.KEY_PROG_PREFIX + slug, v);
}
```

为什么执着于"只进不退"：读长文时回头翻资料是常态，如果进度跟着滚动条实时回退，"继续阅读"卡片会在 63% 和 12% 之间反复横跳。Kindle 的断点永远是你走过的最深处，这是被验证过多年的语义。

**已读不存储、只派生**：进度 ≥ 96 判定读完（`DONE_PCT`）。为什么不另存一个 `isRead` 布尔？因为"读完"和"进度满了"是同一件事的两个说法，存两份必然打架——布尔忘了置位而进度已满时，卡片该信谁？派生则永不出错，还省一个键。

96 而不是 100：滚动到底部常伴随弹簧回弹（EdgeEffect.Spring），采样很难稳定踩在 100 上；96 足以覆盖"眼睛扫过最后一行"的语义。

## 二、恢复时机的坑：布局未成，滚动无效

第一版把恢复写在 `aboutToAppear` 里直接 `scroller.scrollTo(...)`，纹丝不动。原因：Markdown 引擎是异步渲染，页面创建时内容高度还是 0，自然滚不动。

正确的做法是等两个信号：

1. **布局高度就绪**：Scroll 自身 `onAreaChange` 记视口高 `viewportH`，内容根节点 `onAreaChange` 记总高 `contentH`；
2. **渲染完成**：引擎 `complete` 回调后延迟 300ms 等布局稳定，按 `进度% × (contentH - viewportH)` 恢复。

恢复动作做成幂等的一次性闸门（`restorePending` 标记）：两个高度回调谁后来谁触发，只执行一次，不会重复滚动。

另一个细节：内容不超过一屏（`contentH - viewportH <= 0`）时，整篇可视即读完，直接置 100%——短文不该永远停留在 0。

## 三、会话统计：跨天、防虚计

时长用最朴素的 `onPageShow` / `onPageHide` 计时：页面可见时记 `sessionStart`，不可见时结算差值秒数。三个要点：

- **跨日清零**：今日秒数带所属日键（yyyyMMdd），新的一天自动归零；
- **会话封顶**：单次结算最长 3600 秒。页面被切到后台过夜是常态，不封顶的话"今日阅读 9 小时"就是自欺欺人的数字；
- **连续天数**：结算时若上次活跃日是昨天则链长 +1，否则重新起链；展示时今日或昨日活跃才算数——"连续 3 天"在第二天打开时仍显示，第三天不读就归零，和打卡产品的直觉一致。

## 四、剩余分钟：一个诚实的估算

预计时长 = `max(1, round(字数 / 400))`，中文均速 400 字每分钟是保守值；剩余分钟 = 预计时长 × 未读比例，下限 1 分钟（0 分钟看起来像"没内容"）。悬浮胶囊只在进度处于 0 到 100 之间时出现，读完即消失——不打扰阅读，但随时能问一句"还剩多久"。

## 五、读后引导：让阅读不断链

读完最自然的动作是"下一篇"。两个设计决策：

- **下一篇 = 列表相邻项**，不做"智能推荐"。构建手记有线性叙事——从工程初始化一路读到页面导航，列表顺序就是作者意图；顺带免维护、可预期；
- **跳转用 `router.replaceUrl` 替换当前页**，不压栈。连续读五篇，路由栈永远是 [首页, 文章]，返回键一步回家，不会陷入"返回-返回-返回-返回-首页"的地狱。

相关阅读做补充：同分类 +3 分、每同标签 +2 分，排除自身与下一篇，取前三。

## 六、列表回显：ForEach key 的小心机

详情页读完返回列表，卡片要显示"✓ 已读"。坑在于：卡片组件创建时自读进度存进内部状态，父页面刷新时**子组件内部状态不会跟着更新**——进度变了，卡片还是旧模样。

解法土但有效：列表页 `onPageShow` 自增 `refreshTick`，拼进 ForEach 的 key 生成函数——`slug_tick`。tick 变了，key 变了，框架视其为新组件，重建并重新读进度。代价是整列表重建一次，十几篇的列表完全无感。

## 结语

阅读闭环的本质不是堆功能，而是把散落的文章变成一条能接着读的链路：记住位置、恢复现场、算清时间、指出下一步。全部本地 preferences，零网络零权限——离线应用也能有阅读产品的完成度。

# 平板宽屏适配实录：左侧导航栏、内容限宽与仪表盘冻结修复

应用最初按手机布局设计。跑到 2400×1600 的平板模拟器上一看，问题一目了然：整行拉伸、右侧留白、信息密度骤降。这轮迭代把宽屏当成一等公民重做布局，顺带修掉一个状态刷新的隐蔽 bug。

## 问题：平板上的一片空白

平板横屏下，应用沿用手机布局横向铺满，右侧出现大片空白，信息密度骤降。手机上撑满 1080px 宽的一张文章卡片，在平板上被拉到 2000px 出头——一行文字的阅读距离远超舒适区，页面元素数量却没变，视觉上"空得发慌"。

## 方案：断点检测与布局切换

宽屏判定用窗口实际宽度做断点：达到 840vp 即切换宽屏布局，窄屏保持底部三 Tab。

```typescript
// AppTheme.ets
static readonly CONTENT_MAX_WIDTH: number = 720;
static readonly BREAKPOINT_WIDE: number = 840;

// Index.ets
.onAreaChange((oldArea: Area, newArea: Area) => {
  this.isWide = (newArea.width as number) >= AppTheme.BREAKPOINT_WIDE;
})
```

选 onAreaChange 而不是启动时一次性判定，是为了实时响应横竖屏旋转与自由窗口拉伸。宽屏布局三处联动：

- 左侧导航栏（240vp）：应用名加学习、知识库、我的三项，替代底部 Tab；
- Tabs 的 barHeight 置 0、scrollable 关闭，切换只走导航栏点击；
- 各内容页限宽 720vp 居中（见下节）。

导航项的选中态直接读 @State，@Builder 只传字面常量——这一点稍后会被仪表盘一节反面印证。

## 内容限宽：720vp 居中

宽屏下内容列限宽 720vp 并居中，避免一行文字横贯整块屏幕。落地是 14 个页面根容器统一加约束：

```typescript
.constraintSize({ maxWidth: AppTheme.CONTENT_MAX_WIDTH })
```

对齐上踩了一个坑：Scroll 默认把不足一屏的内容在视口里垂直居中——限宽后的答题页、设置页内容偏矮，整页"悬浮"在视口中间，看起来像 bug。修法按页面根容器二选一：

- 根容器是 Scroll 的，显式 `.align(Alignment.Top)`，内容从顶部排起、水平方向仍居中；
- 根容器是 Column 的，`alignItems(HorizontalAlign.Center)` 配合限宽列。

两种写法效果一致：垂直贴顶、水平居中。默认值不可依赖，宽屏适配里对齐方式必须显式声明。

## 仪表盘冻结：按值传参的 @Builder 不吃状态更新

统计仪表盘曾出现冻结：阅读分钟与连续天数永远停在首次渲染时的值，此后不再更新。排查后定位到 @Builder 的按值传参：

```typescript
// ❌ 冻结写法：statCell(label, value) 按值传参，@Prop 更新无法穿透 Builder
@Builder statCell(label: string, value: number) { /* Text(value) ... */ }
this.statCell('今日阅读', this.todayMinutes)

// ✅ 修复写法：数字直接内联绑定 @Prop 字段
Text() {
  Span(`${this.todayMinutes}`)
}
```

机制：@Builder 的参数按值捕获，调用处的状态变化不会触发 Builder 内部绑定刷新，三格数字因此在首次渲染后被"焊死"。修复是把三格改成直绑 @Prop 的内联结构。规约随之更新：需要响应状态的 UI 单元一律内联直绑；@Builder 只承担纯静态的结构复用，且参数只传字面常量。

## 收尾

三端验证后，平板与 2in1 均为左侧导航栏加居中内容列，窄屏手机布局不变。平板 2400×1600 与 2in1 1920×1080 下导航栏、限宽、贴顶对齐全部生效，旋转与拉伸窗口实时切换；手机端布局零回归。这轮的收获可以压缩成两句话：断点切换靠监听而不是快照，状态渲染靠直绑而不是转发。

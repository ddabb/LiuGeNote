
# 主线程耗时与高频刷新：两个最常见的性能陷阱

ArkUI 的 UI 渲染、事件分发、状态计算都跑在主线程。掉帧的元凶九成是这两类：**一次性卡太久**，或**刷新太频繁**。

## 陷阱一：生命周期里干重活

```typescript
aboutToAppear(): void {
  // ❌ 全文搜索语料构建 + 逐篇解码，几百毫秒起步
  this.buildSearchCorpus();
}
```

页面还没画出来就先卡住——冷启动白屏、切页转圈，多半是它。

### 治理：挪、拆、延后

1. **挪**：纯计算（解析、排序、编码）放 `TaskPool`，主线程只接收结果；
2. **拆**：无法异步的分批做，先渲染首屏数据，剩余的 `setTimeout` 补齐；
3. **延后**：非首屏必需的初始化（搜索语料、PDF 探测）延迟到首次使用时再做——懒加载不只是组件的事，**数据也可以懒加载**。

```typescript
// ✅ 语料构建推迟到首次搜索
private ensureCorpus(): void {
  if (this.corpus.size > 0) {
    return;
  }
  // ……此时用户已有预期（正在搜索），几百 ms 可接受
}
```

## 陷阱二：高频状态刷新

```typescript
// ❌ 阅读进度每次滚动都 putSync+flush，还触发全页状态更新
onScroll(percent: number): void {
  this.progress = percent;        // 高频 @State 更新
  this.store.putSync('p', percent);
  this.store.flush();             // 高频磁盘 IO
}
```

滚动每秒触发几十次回调，每帧都带着磁盘落盘和组件重绘。

### 治理：节流与收窄

1. **节流**：进度持久化限制在「每 N 秒/每变化超阈值」才执行一次，退出页面时兜底保存一次；
2. **收窄刷新范围**：只让显示进度的组件订阅这个状态（子组件持有），别把高频值挂在页面级 `@State` 上；
3. **换低频回调**：能用 `onScrollEnd` / `onTouch(Up)` 就不用 `onScroll`。

## 排查工具

- DevEco Profiler 的 **Frame** 视图：看掉帧时刻主线程在跑什么；
- 打点对照：进入/完成各一条 hilog，耗时超 50ms 的函数逐个治理；
- 真机为准：模拟器帧率数据不可信，性能结论一律真机复测。

## 性能预算参考

| 操作 | 预算 |
|---|---|
| 生命周期内同步逻辑 | < 50ms |
| 单帧渲染 | 16.6ms（60fps） |
| 高频回调内的单次处理 | < 2ms |

## 一句话总结

**重活出主线程，高频做节流**。两条做到，绝大多数掉帧和转圈都会消失。

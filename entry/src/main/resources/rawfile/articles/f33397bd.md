
# 冷启动优化：从点图标到首屏可交互

用户点图标 → 首屏可交互，中间的每一毫秒都在消耗耐心。冷启动优化先搞清楚：时间花在哪了。

## 启动链路与耗时大户

```
点图标 → 进程创建 → AbilityStage/EntryAbility.onCreate
       → onWindowStageCreate(loadContent) → 首帧渲染 → onPageShow → 可交互
```

| 阶段 | 典型耗时大户 |
|---|---|
| onCreate | 全局初始化：preferences 打开、题库加载、字体解码 |
| loadContent | 首页组件树构建 |
| 首帧渲染 | 大列表一次性构建、大图解码 |

## 优化一：onCreate 里的初始化做减法

```typescript
onCreate(): void {
  // ❌ 启动全干：所有仓库、全部偏好、题库、字体，一口气初始化
  // this.initEverything();

  // ✅ 只留首屏必需
  this.repo.init(this.context);        // 仓库注入 context：必留（轻）
  QuizManager.init(this.context);      // preferences 打开：轻，可留
  // 字体解码、PDF 服务探测、搜索语料 → 推迟到首屏渲染完成后
}
```

判断标准一句话：**首屏第一眼用不到的，都不配在 onCreate 里跑**。

## 优化二：首屏数据精简

```typescript
// ❌ 首页一次性构建全部 30 篇文章的完整卡片树
// ✅ 首屏只渲染前 6 篇 + LazyForEach 兜底
```

配合「数据懒加载」：首页列表只读 index.json（元数据），正文等点开再读。

## 优化三：字体与大资源的懒加载

内置字体动辄几 MB，`FontRegistry` 注册时的解码开销直接压在启动路径上：

- 非首屏必需字体（如全文阅读字体）→ 首次进入阅读页再注册；
- 首页只用系统字体兜底，或同步注册一款小字号子集。

## 优化四：页面骨架提前渲染

数据没到也要先给结构：骨架屏（Skeleton）或默认值渲染，数据到了再填充。**「先看到页面再等数据」永远比「白屏等齐」体验好**。

## 测量：没有数据就没有优化

```bash
# 启动耗时打点：onCreate / loadContent / onPageShow 各一条 hilog
hilog.info(DOMAIN, 'Launch', 'onCreate done at %{public}d', Date.now());

# 查看启动耗时
hdc shell aa start -b com.example.app -a EntryAbility   # 启动并计时
# DevEco Profiler 的 Launch 视图：分阶段耗时一目了然
```

优化前后各测三遍取中位数，**真机为准**（模拟器数据不可信）。

## 预算与效果参考

| 指标 | 目标 |
|---|---|
| 冷启动（点到首帧） | < 2s，优秀 < 1s |
| onCreate 内同步逻辑 | < 50ms |
| 首屏列表组件数 | 首屏可见数 + 预加载缓存 |

## 踩坑记录

1. onCreate 里同步读大文件（几 MB 正文缓存）——最隐蔽的启动杀手；
2. 首页 build 里塞了统计计算——渲染路径越短越好；
3. 优化完忘了上真机复测，低端机效果归零。

## 一句话总结

**首屏必需的同步做，其余全部延后**：初始化、字体、数据、语料，四个懒加载下来，冷启动就轻了。

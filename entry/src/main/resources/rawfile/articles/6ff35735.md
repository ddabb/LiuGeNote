
# git hooks 行数护栏：把"别写太长"变成提交门禁

"单文件别超过一千行"——这类约定几乎每个项目都有，也都在第三次赶工时失守。本文记录把这句口头禅变成 git 提交门禁的过程。

## 一、痛点：文件是怎么胖起来的

没有恶意，全是合理需求的叠加：详情页今天加个导出，明天补个分享，后天塞个进度追踪。回过神来，`ArticleDetailPage` 已经近六百行。单文件膨胀的代价不在运行时，在维护时：review 时没人愿意通读千行 diff，合并冲突的噩梦半径随行数增长，拆分的心理成本也随行数增长——越晚拆越难拆。

结论：行数约束必须在**提交时**拦截，而不是事后重构。

## 二、hooks 随仓库走：core.hooksPath

git 默认的 `.git/hooks/` 目录不在版本库内，每个克隆都要手工安装，等于没有约束力。解法很老但很稳：

```
.githooks/
└── pre-commit        # 入库，随仓库分发
```

```
git config core.hooksPath .githooks
```

本机执行一次配置，仓库里的 hooks 此后对所有提交生效（配置本身不进版本库，README 里注明即可）。

## 三、护栏规则：三条

1. **新增/修改文件 ≤ 900 行**（物理行，含空行与注释）；
2. **存量超标文件登记白名单**（`scripts/size_whitelist.json`），允许存在；
3. **白名单只减不增**：登记了 1200 行的文件，可以维持、可以往下拆，但**不许再长一行**。

为什么口径选物理行而不是"有效代码行"？因为"有效"有歧义——注释算不算？空行算不算？有歧义就会有争论，有争论就会有人绕过。物理行与 IDE 行号完全一致，`Ctrl+G` 跳过去即可对质，零争议。

## 四、为什么"只减不增"是灵魂

如果白名单可以随手加条目、加上限，护栏就成了橡皮图章：超标 → 登记白名单 → 继续写 → 再超标……规则可被廉价修改时，就一定会被修改。

只减不增把白名单变成**单向棘轮**：存量被冻结在当前水位，增量被 900 硬顶。文件要么维持，要么在持续修改中自然拆分（拆到 ≤900 行后条目移除，`--check` 会主动提示）。数月后回看，白名单的收缩曲线就是代码健康度的直观曲线。

## 五、实现：一个脚本三种用法

`scripts/code_stats.py` 纯标准库实现，不依赖任何第三方包：

```
py -3 scripts/code_stats.py --check            # 护栏校验（pre-commit 调用，违规退出码 1）
py -3 scripts/code_stats.py --top 20           # 行数榜：该拆谁一目了然
py -3 scripts/code_stats.py --init-whitelist   # 按当前状态生成/重置白名单
```

pre-commit 里只做一件事：跑 `--check`，失败即拒绝提交。输出消息刻意保持 ASCII——hook 的执行环境（sh、管道、各种控制台代码页）里，中文提示是乱码重灾区。

## 结语

行数不是质量的充分条件，但是最便宜的健康度代理指标。900 这个数字不重要，重要的是"约束发生在提交时"和"棘轮只朝一个方向转"。两行 git config 加一个百余行的脚本，把"别写太长"从一句嘱咐变成一道门禁。


# 包体积优化：资源、字体与 so 治理

应用包从 10MB 涨到 50MB 不知不觉——每张「先放进去再说」的资源都在投票。包体积直接影响下载转化率，值得当 KPI 管。

## 包体积的构成

```
entry.hap
├── resources/        图片、字符串、rawfile（内置字体、离线数据）★ 通常最大
├── libs/             so 原生库（按 ABI 分 armeabi-v7a / arm64-v8a / x86_64）
├── ets/              编译后的字节码 + 依赖库
└── 配置文件          module.json5 等（可忽略）
```

## 大头一：内置字体

中文字体动辄 5~15MB，是内容类应用的体积之王：

1. **子集化**：中文字库 3 万+ 字，实际用到几千字——用 fonttools（`pyftsubset`）按应用字符集裁剪，10MB 字体常能压到 1~3MB；
2. **按需加载**：阅读字体不随首页加载，放 rawfile 延迟注册（兼得启动速度）；
3. **woff2 优先**：同款字体 woff2 比 ttf 小 30% 左右（需确认运行时支持后选用）。

## 大头二：图片资源

- 压缩：PNG 走 pngquant / WebP；照片类直接 WebP；
- 尺寸：显示 96×128 就存 192×256（两倍 Retina 余量），**别存 1000×2000 原图**；
- 矢量优先：图标一律 SVG，单色图标可用字体图标方案；
- 复用：同一资源一份，删掉 `cover_final_2.png` 这类「版本化石」。

## 大头三：rawfile 离线数据

内容随包分发的应用要面对一道选择题：

| 策略 | 包体积 | 体验 |
|---|---|---|
| 全量内置 | 大 | 纯离线，上架即用 ★本应用选择 |
| 首次联网拉取 | 小 | 首启必须联网，审核也敏感 |

全量内置时：数据先去重再打包、Markdown 精简示例代码中的冗余空白、图片外链不落盘。

## so 库与三方依赖

1. ABI 裁剪：真机发布只留 `arm64-v8a`（模拟器调试再临时开 x86_64）；
2. 依赖审计：`ohpm ls` 看引入的三方库，未用的、重复功能的清掉；
3. 大依赖替换：一个 Markdown 渲染库带进 prism 高亮全家桶——按需引入子模块。

## 工程化：包体积护栏

人工看不住包体，脚本才看得住：

```
.git/hooks/pre-commit
  └── code_stats.py 检查 entry 目录体积
      超过阈值 → 拒绝提交（白名单机制允许显式豁免）
```

本项目的做法：`scripts/code_stats.py` + 白名单 JSON，pre-commit 时对 `resources/`、`rawfile/`、字体文件分别设阈值——**体积膨胀在提交那一刻就被拦截**，而不是上架前。

## 踩坑记录

1. 优化完字体忘了验证渲染：子集化漏字导致阅读页生僻字变豆腐块——子集字符集要覆盖全部内容文本；
2. 删资源不看引用：`$r` 引用删了编译才报错，先全局搜索再删；
3. 只测 debug 包：release 包有裁剪与混淆，体积结论以 release 为准。

## 一句话总结

**字体做子集、图片控尺寸、数据做精简、体积设护栏**——四步走，包体可控且不再悄悄膨胀。

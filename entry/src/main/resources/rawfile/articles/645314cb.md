
# 条件渲染与循环渲染：if、ForEach 的刷新规则

`build()` 里只允许两类控制结构：`if/else` 条件渲染和 `ForEach` 循环渲染。它们的**刷新规则**决定了「改了数据 UI 不动」还是「改了数据状态丢了」。

## if/else：销毁与重建

```typescript
build() {
  Column() {
    if (this.isLoading) {
      LoadingIndicator()          // 分支 A
    } else {
      ArticleList({ list: this.list })   // 分支 B
    }
  }
}
```

核心规则：**分支切换 = 销毁旧组件 + 创建新组件**。

推论：

- 分支内组件的**本地状态不保留**：从 B 切回 A 再切回 B，B 里子组件的 `@State` 归零；
- 频繁切换的分支开销不小——纯视觉差异（文字/颜色变化）**别用 if**，改属性绑定；
- 条件里只能读状态，不能改状态。

```typescript
// ❌ 用 if 切换颜色：销毁重建，闪烁
if (this.active) { Text('标题').fontColor('#C00') } else { Text('标题').fontColor('#666') }

// ✅ 属性绑定：同一个组件，属性变化
Text('标题').fontColor(this.active ? '#C00' : '#666')
```

## ForEach：按键 diff

```typescript
ForEach(this.articles, (item: ArticleMeta) => {
  ArticleCard({ meta: item })
}, (item: ArticleMeta) => item.slug)   // 第三个参数：键生成器
```

刷新算法（简化）：

1. 新旧两轮各生成一批 `(key, 组件)`；
2. **key 相同** → 复用旧组件，更新绑定数据；
3. **key 是新的** → 创建；
4. **旧 key 消失** → 销毁。

因此：

- **键必须稳定且唯一**：用业务 id（slug/guid），别用 `JSON.stringify(item)`（内容变了键就变）或下标（错位复用）；
- 键相同的组件**内部状态保留**——这是「列表项展开态不丢」的前提。

## 「列表不刷新」的三个根因

| 根因 | 症状 | 修法 |
|---|---|---|
| 数组项是嵌套对象，改属性 | @State 数组本身没变 | 拆子组件 + @ObjectLink（V1）或迁 V2 @Trace |
| 直接改数组内部再赋回同引用 | 引用相同，浅比较跳过 | 生成新数组：`this.list = this.list.concat()` 或整体替换 |
| 键生成器漏写 | diff 退化，行为不稳定 | 必须写第三个参数 |

## 嵌套渲染控制

```typescript
ForEach(categories, (cat: Category) => {
  Text(cat.name)
  ForEach(cat.articles, (a: ArticleMeta) => {
    ArticleCard({ meta: a })
  }, (a: ArticleMeta) => a.slug)
}, (cat: Category) => cat.name)
```

ForEach 可以嵌套，键在**同层兄弟之间**保证唯一即可。

## 踩坑记录

1. if 分支里持有计时器/监听器，切走时要在 `aboutToDisappear` 里清理——销毁不会自动帮你停；
2. ForEach 数据源是普通数组时用 `@State` 观察；超长列表换 `LazyForEach`；
3. 条件渲染里 `else if` 链过长说明该拆组件了。

## 一句话总结

**if 是销毁重建，ForEach 是按键复用**：纯视觉变化用属性绑定，列表刷新靠稳定键，嵌套对象交给子组件观察。

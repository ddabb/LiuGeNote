
# 三端上架截图实录：密度持久化、渲染卡死与像素级验收

应用市场提审要三端截图，规格各有硬指标，而生产这批截图的环境里恰恰"看不了图"。本文记录全程脚本化的截图方案，以及两个真 bug：2in1 模拟器密度被 userdata 持久化导致"元素太少"，和 render_service 系统卡死产出故障帧。

## 一、需求与总体方案

上架规格：手机 9:16 且 ≥1080×1920、平板 3:2 且 ≥1920×1280、2in1 16:9 且 ≥1920×1080，各 3~10 张，JPEG ≤5MB。五个页面各取一张：首页、分类列表、搜索（带结果）、设置、文章阅读，三端共 15 张。

截图完全脚本化，三件套：

- **取图**：`hdc snapshot_display`——直接抓显示合成器输出，分辨率精确等于物理分辨率；
- **导航**：`uitest dumpLayout` 拿 ArkUI 无障碍树，解析可点元素的物理像素坐标，`uitest uiInput click` 逐个点击；输入用 `uiInput inputText`，中英文都能直接注入；
- **验收**：每张截图先 dump 布局确认页面状态，截完校验尺寸/比例/文件大小，必要时上像素探针。

手机（1080×1920）与平板（2400×1600）一波通过。2in1 翻车了。

## 二、Bug 一：2in1"元素太少"——密度被 userdata 持久化

首版 2in1 截图被否：**应用呈现的元素太少了**。1920×1080 的屏，应用窗口里只装下约 590×229vp 的内容——首页只有标题、chips 和一张卡片的边缘。

### 现象

布局解析给出关键数字：PageHeader 的 34vp 图标在屏幕上占 111px，折算有效渲染密度 ≈522，而 config.ini 里写的是 160。dock 高 214px、占屏高 20%（真机 MateBook 约 10%）。

### 排查

按顺序排掉这些路：

- **改 config 无效**：`hw.lcd.density` 先后设 200、160，两次冷启动后渲染纹丝不动——而同一份 config 里的分辨率与物理尺寸都生效了（RenderService dump 确认）。唯独密度不动。
- **无 wm 命令**：系统里没有 Android 风格的 `wm density`。
- **param 不可用**：查询报 1002/106（not found），`param ls -r` 直接 "Forbid to list parameters"。
- **设置应用打不开**：`aa start` 启动设置的所有 ability 均报 Error Code:10104001 "ability not installed"，显示缩放页无法到达。

### 根因

实例创建时的配置是 3120×2080 @ density 304。密度在**首次启动时被写进 userdata 持久化**（叠加约 1.7 倍缩放，522 ≈ 304×1.72），此后每次启动读持久化值，config 改动不再参与推导；而分辨率、物理尺寸是启动时实时读的，所以改了就生效——这解释了"同一份 config，一半生效一半不生效"的诡异现象。

### 解决：官方擦除 + 冷启动

devecocli 提供了正门：

```bash
devecocli emulator stop Copybook2in1
# config.ini 三个密度相关键统一到 240dpi：
#   hw.lcd.density=240 / phy 203×114mm / diagonalSize=9.18
devecocli emulator start Copybook2in1 --boot-mode reset
```

`--boot-mode reset` 清空数据后冷启动。首次起来只有锁屏，上滑解锁即进桌面（OOBE 向导被镜像预置跳过）。验证：dock 从 214px 降到 **99px**（屏高 20%→9.2%，贴近真机），34vp 图标 51px，折算有效密度 **240，与配置分毫不差**。应用画布从 577×324vp 扩到 1280×720vp——首页能同时装下统计行、双 chips、应用自述和三张完整文章卡片。

**教训**：模拟器实例的显示配置分两层——config.ini 是"部署输入"，userdata 里还有一份"运行时持久化"。想让显示配置重新推导，必须擦数据（reset），重启不够。

## 三、Bug 二：render_service 卡死，截出故障帧

重截进行到第 2 张（分类列表）后，应用突然从布局树里消失，进程也没了。faultlog 里躺着真凶：

```
/data/log/faultlog/faultlogger/sysfreeze-render_service-1003-*.log
Reason: SERVICE_BLOCK
Watchdog: thread(RenderService) blocked 5s
```

渲染服务主线程阻塞 5 秒被 watchdog 处理，应用进程被连带带走。坏消息是：**那张"分类列表"恰好是在卡死窗口里截的**——布局 dump 显示页面正常，但 snapshot 拿到的是故障瞬间的异常帧，直到人审才发现"图 2 错误"。

重截流程加了三道保险：

1. **截前**：dump 布局，确认目标页面元素齐全；
2. **截后**：立刻再 dump，确认应用存活、页面未变（卡死会在这一步暴露）；
3. **像素校验**：按当前布局里五个分类行的精确包围盒，逐行统计截图像素深色占比——23%~27%，五个标题全部在位；配合亮度均值/方差排除黑屏，与首页基准图 diff（均值差 89.2）排除残影。

## 四、坐标不能跨页面复用

复盘还发现一个小坑：搜索/设置/分类页的返回键在内容列内（x≈465），而文章详情页用全宽头部，返回键在最左（x≈49）。同一个"‹"，坐标差 400+px——从文章页返回时沿用旧坐标，点中的是标题文本，毫无反应。导航坐标永远以**当次 dumpLayout** 为准，不做跨页面假设。

## 五、结果

三端 15 张全部通过规格校验：

| 端 | 分辨率 | 比例 | 张数 | 单张大小 |
|---|---|---|---|---|
| 手机 | 1080×1920 | 9:16 | 5 | 51~193KB |
| 平板 | 2400×1600 | 3:2 | 5 | 77~215KB |
| 2in1 | 1920×1080 | 16:9 | 5 | 65~132KB |

配套产出 17 字推荐语与应用描述。方法论沉淀一句话：**在"看不了图"的环境里，截图验收必须是三件事的组合——布局树确认状态、文件元数据确认规格、像素探针确认内容。三者缺一，故障帧就会混过流水线，直到人审才被发现。**
